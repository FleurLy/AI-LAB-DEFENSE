# Testing the LLM Pipeline on Emails

This guide explains how to test the complete pipeline:

```text
.eml file
  → SMTP extraction pipeline
  → normalized JSON
  → FastAPI /analyze API
  → Jev (security decision)
  → GPT (report generation)
  → JSON and Markdown results
```

## Prerequisites

- Python 3.11 or newer;
- Docker with Docker Compose for the SMTP pipeline;
- a valid OpenRouter API key;
- the `llm/` and `extraction/` folders placed next to each other.

From the `llm/` directory, prepare the Python environment:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
```

Configure at least the following variables in `llm/.env`:

```dotenv
OPENROUTER_API_KEY=your_openrouter_key
LLM_PROVIDER=openrouter
JEV_MODEL=typesafe/jev-router
LLM_MODEL=openai/gpt-4o-mini
LLM_TEMPERATURE=0
LLM_TIMEOUT_SECONDS=30
```

`JEV_MODEL` performs the security analysis.

`REPORT_MODEL` generates the report. If it is empty, the program uses `LLM_MODEL`.

After modifying `.env`, restart the API because the configuration and models are cached.

## 1. Start the SMTP pipeline

In a first terminal:

```bash
cd ../extraction
cp .env.example .env
sudo docker compose up --build
```

The SMTP server should listen on:

```text
localhost:1025
```

Received emails are normalized into:

```text
extraction/data/normalized/
```

## 2. Start the LLM API

In a second terminal:

```bash
cd ../llm
source .venv/bin/activate
uvicorn app.main:app --reload
```

Check that the API is running:

```bash
curl --fail http://127.0.0.1:8000/health
```

Expected response:

```json
{
  "status": "ok"
}
```

The analysis pipeline is fixed:

```text
Normalized JSON
  → Jev
  → SecurityAnalysis
  → GPT
  → SecurityReport
```

Jev is responsible for making the structured security decision.

GPT receives the result produced by Jev and generates the human-readable report.

## 3. Test the complete dataset

In a third terminal, from the `llm/` directory:

```bash
source .venv/bin/activate
python scripts/run_dataset.py
```

By default, the runner recursively scans all `.eml` files under:

```text
../extraction/
```

This includes files located in folders such as:

```text
samples/
datasets/
```

The runner ignores:

```text
../extraction/data/
```

because this directory contains files generated by the SMTP pipeline itself.

Emails are processed sequentially.

For each `.eml` file, the runner:

1. calls `extraction/scripts/replay.py`;
2. sends the email to the local SMTP server;
3. waits for the corresponding normalized JSON file;
4. sends the JSON to `http://127.0.0.1:8000/analyze`;
5. saves the final JSON response;
6. locally generates a Markdown report from the JSON response without any additional LLM call.

The complete flow is therefore:

```text
.eml sample
   ↓
replay.py
   ↓
SMTP server
   ↓
extraction pipeline
   ↓
normalized JSON
   ↓
POST /analyze
   ↓
Jev
   ↓
SecurityAnalysis
   ↓
GPT
   ↓
SecurityReport
   ↓
JSON result
   ↓
Markdown generation
```

## Testing only one folder

To test only the examples inside `samples/`:

```bash
python scripts/run_dataset.py --samples ../extraction/samples
```

To test only the phishing validation dataset:

```bash
python scripts/run_dataset.py \
  --samples ../extraction/datasets/phishing_validation/emails
```

To increase the normalization and API timeouts:

```bash
python scripts/run_dataset.py \
  --normalization-timeout 120 \
  --api-timeout 180
```

To display all available options:

```bash
python scripts/run_dataset.py --help
```

## Results

All generated results are written to:

```text
llm/data/results/
```

For example:

```text
data/results/
├── results.json
├── phishing_link.json
├── phishing_link.md
├── simple_text.json
└── simple_text.md
```

The `data/results/` directory may already contain results from previous executions.

This is expected and is not a problem.

To run all tests again and regenerate the results, simply rerun:

```bash
python scripts/run_dataset.py
```

The runner will process the dataset again and produce fresh outputs.

### `results.json`

`results.json` contains the global execution results for all tested emails.

For each email, it can contain information such as:

- the source `.eml` file;
- the normalized JSON;
- the API response;
- the HTTP status;
- execution duration;
- possible replay errors;
- possible normalization errors;
- possible API errors.

### `<sample>.json`

Each individual JSON file contains the final response returned by:

```text
POST /analyze
```

For example:

```text
phishing_link.json
```

contains the complete structured security analysis and report for the corresponding email.

### `<sample>.md`

Each Markdown file contains the same result in a more human-readable format.

For example:

```text
phishing_link.md
```

may contain:

```markdown
# Email Security Analysis

## Overview

- Social engineering probability: 99%
- Attack type: credential theft
- Requested action: provide credentials

## Summary

The email appears to impersonate a trusted service and attempts to obtain the user's credentials.

## Evidence

- suspicious sender identity
- failed authentication checks
- suspicious URL
- artificial urgency

## Recommended actions

- Do not interact with the links.
- Report the email to the security team.
- Quarantine the message.
```

The Markdown is generated directly from the final JSON response.

No additional LLM call is performed for Markdown generation.

## Automatic SUCCESS / FAIL verdicts

For files whose path contains either:

```text
benign/
```

or:

```text
suspicious/
```

the dataset runner can infer the expected binary class directly from the file path.

The Markdown report then starts with a verdict.

The rules are:

```text
benign/ + attack_type == "none"
→ SUCCESS

benign/ + attack_type != "none"
→ FAIL

suspicious/ + attack_type != "none"
→ SUCCESS

suspicious/ + attack_type == "none"
→ FAIL
```

In other words:

- a benign email should not be classified as an attack;
- a suspicious email should be classified as some form of attack.

For datasets whose path does not contain `benign/` or `suspicious/`, the runner searches for a `manifest.csv` under `extraction/`. It resolves each manifest `file_path` and maps the ground-truth values as follows:

```text
safe, benign, or 0       → expected benign
phishing, suspicious, or 1 → expected suspicious
```

The ground-truth label is loaded separately and is used only after the API response has been received. It is never inserted into the normalized JSON or sent to Jev or GPT. A file receives no verdict only when neither its path nor a manifest entry provides an expected class.

## Testing a single normalized JSON without SMTP

If an email has already been normalized, the SMTP and extraction steps can be skipped.

From the `llm/` directory:

```bash
curl --fail-with-body http://127.0.0.1:8000/analyze \
  -H 'Content-Type: application/json' \
  --data-binary @examples/email_analysis.json
```

This directly tests:

```text
normalized JSON
  → FastAPI
  → Jev
  → GPT
  → final result
```

## Automated tests without external API calls

The Python test suite uses mocks and does not contact OpenRouter.

Run all tests with:

```bash
python -m pytest -q
```

To test only the dataset runner:

```bash
python -m pytest -q tests/test_run_dataset.py
```

## Common errors

### `422 Unprocessable Content`

The normalized JSON does not match the FastAPI input schema.

Check:

```text
api_response.detail
```

inside:

```text
data/results/results.json
```

### `503 configuration_error`

The OpenRouter API key or a required model identifier is missing.

Check the variables inside:

```text
llm/.env
```

especially:

```dotenv
OPENROUTER_API_KEY=
JEV_MODEL=
LLM_MODEL=
```

After modifying `.env`, restart FastAPI.

### `502 provider_error`

OpenRouter or the selected model rejected the request.

Possible causes include:

- invalid model identifier;
- unavailable model;
- provider-side error;
- invalid API credentials;
- unsupported structured output.

### `504 analysis_timeout`

The model did not answer before the configured timeout.

Increase:

```dotenv
LLM_TIMEOUT_SECONDS=60
```

or another appropriate value, then restart the API.

### `ERROR (replay)`

The `.eml` file could not be sent to the SMTP pipeline.

Check that the SMTP container is running and listening on:

```text
localhost:1025
```

You can inspect the extraction terminal or Docker logs.

### `ERROR (normalization)`

The email was sent successfully but the expected normalized JSON was not generated.

Check the extraction pipeline logs:

```bash
cd ../extraction
sudo docker compose logs
```

### `ERROR (api)`

The normalized email was generated correctly, but the FastAPI analysis request failed.

Check that FastAPI is running on:

```text
http://127.0.0.1:8000
```

Verify the health endpoint:

```bash
curl --fail http://127.0.0.1:8000/health
```

Then inspect the recorded API response inside:

```text
data/results/results.json
```

## Runner behavior on errors

The runner processes emails sequentially.

If one email fails, the script does not stop immediately.

Instead, it records the error and continues with the next email.

This allows the complete dataset to be tested even if one or several samples fail.

The runner exits with status code:

```text
0
```

if all tests complete successfully.

It exits with:

```text
1
```

if at least one test fails.
